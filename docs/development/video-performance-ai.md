# Video performance and automation

The editor uses shared core planners for GUI and MCP edits, immutable render snapshots, and bounded background work. The primary controls and limits are discoverable with `get_video_capabilities`; `get_action_schema` returns the complete schema of a named action.

## Editing with an AI client

1. Call `get_video_capabilities`, then `get_action_schema` for the actions needed. Search results retain the full input/output schemas and side-effect annotations. Results expose native MCP `structuredContent` and retain the existing JSON text block for older clients.
2. Read `get_timeline_snapshot` for an explicit sequence. Select tracks and a time range when possible. Pages contain stable IDs, source/timeline timing, formats, asset/proxy metadata, and a document revision. The default page is 200 clips; the maximum is 1,000. Continue with the same scope and the returned offset and revision. A changed document rejects continuation instead of silently shifting clips between pages.
3. Use `render_frames_at` for visual inspection. It returns up to 12 PNGs or a contact sheet, with tick, revision, format, quality, request ID, and tile coordinates. Thumbnails default to a 640-pixel long edge, have a 1,024-pixel maximum, and shrink on the GPU before readback. The encoded batch limit is 16 MiB. Use `quality: "full"` to evaluate originals at the full sequence resolution before shrinking.
4. Submit `apply_video_edit_plan` with the inspected `expected_revision`, a unique `request_id`, and ordered operations. Set `dry_run: true` to validate without changing the document. A value such as `{"$ref":"0.clip_id"}` refers to a previous operation's structured result, so a clip can be created and edited in the same plan. IDs generated by a dry run are provisional; use references within the committed plan.
5. Commit the plan with `dry_run: false`. Any failed operation, locked required participant, wrong sequence, or concurrent revision change rejects the whole plan. A successful changed plan creates one undo entry. Repeating the identical committed request returns its receipt without repeating edits. Reusing that ID with different arguments is an error.

Plans support at most 128 operations and a 1 MiB request. Receipts are session-local, retained for up to ten minutes, and bounded to 256 entries / 16 MiB. They are not durable across restarts. Top-level `revision` is the live document revision; operation results describe the isolated planning state. Long-running jobs, filesystem actions, transport, and undo are excluded from plans. Export is a separate operation after the edit succeeds.

Use `ticks_per_second` and `frame_rate` from the snapshot rather than guessing the editor's clock units. Source timing accounts for speed ramps and reverse playback. `source_extent_ticks` covers the visited source interval even when source end precedes source start.

## Transcript and precision workflows

`get_transcript` returns word-timed tokens from an explicit sequence and caption track. Pagination pins a revision. `edit_transcript_word` changes wording without retiming. `delete_transcript_range` and `remove_filler_words` require explicit participating A/V tracks and a ripple/lift choice; linked and required sync-lock tracks must be included and unlocked. Filler discovery is local exact-token matching, with exclusions represented by omitting matches from the removal request. Stale text/timing selections are rejected. The GUI uses the same planners and supports word selection, seeking, wording edits, filler preview, and timeline highlighting.

`precision_trim` names the outgoing/incoming clips and their track. Roll, ripple, and slip modes share the GUI precision editor's planner, including linked media, source bounds, and locked-track checks. Wrap it in an edit plan for dry run and revision safety. The GUI previews candidates separately from the live document and commits once; cancelling restores the live view.

Source audition uses an explicit probed source interval and an independent source clock. It leaves the document and sequence playhead unchanged. `audition_source` requests local playback; `get_engine_status` reports source progress or an audio-device error. `stop_source_audition` releases that output. Audible sources require an audio output device. Nested-sequence navigation restores the parent timeline's view and selection.

Transcript text remains in document/history state. Dedicated transcript wording and selected filler text are redacted from tool audit arguments, including nested edit plans.

## Rendering and memory

Draft processing and source proxy selection are separate controls. Full inspection selects originals **and** a full processing canvas. Render-cache identity includes the processing dimensions, so a Draft result cannot satisfy a Full request. Exact inspections carry a request ID and snapshot generation; they do not accept an old frame at the same tick.

GUI and MCP bridges publish immutable snapshots only when the document revision changes. A temporary format or precision view gets a new publication generation without changing the real revision. Embedded vector content travels with render/export snapshots when needed.

Decode-ring reads do not block the realtime engine on FFmpeg. Missing sources keep the last complete frame and report buffering; incomplete graphs never enter the cache as valid transparent frames. Source preparation, still/vector rasterization, decode workers, and command admission are bounded. Scrub bursts coalesce, while ordered commands retain their relative order and can explicitly report backpressure. Textures retained by the GUI or inspection remain protected from pool reuse.

`get_engine_status` exposes publication/evaluation counters, source readiness, queue admissions/rejections, and managed cache occupancy. Current per-session partitions are 1 GiB of graph results, 256 MiB of uploads, 128 MiB each of still/vector textures, and up to eight 64 MiB decode rings. Two raster jobs are admitted, each with a 128 MiB input/packed-byte limit. One oversized decoded frame can exceed its ring budget and is reported. These figures exclude external texture owners, rendering scratch, FFmpeg, audio, and other sessions; they are not a process RSS guarantee.

## Export and cached playback

Exports freeze the full document revision at admission. The bounded pipeline overlaps rendering/readback with conversion and encoder writes. One queued frame bounds input buffering independently of duration; producer and consumer can each hold another frame. Conversion/encoding scratch, audio PCM, and FFmpeg allocations are separate.

`export_sequences` resolves up to eight destinations against one required revision before admitting any job. Compatible outputs share rendered/read-back frames in groups of at most four. Different sequence formats, dimensions, timing, or source/quality choices render separately. Codec/color/alpha/audio settings remain output-specific. The MCP job registry admits at most four active jobs and returns `JobCapacityExceeded` when full.

Each completed media file publishes through a temporary file beside its destination. Cancellation or failure preserves an existing destination and reaps workers/processes. A batch is not a filesystem transaction: already completed outputs remain if another output fails. Image-sequence publication is atomic per image. Two-pass encoding is explicitly rejected before expensive work and disabled in the GUI until implemented.

Preview zones are undoable document state; encoded chunks are disposable cache state. `set_preview_zones` replaces, frame-snaps, and merges zones. `render_preview`, `cancel_preview`, `clear_preview`, and `get_preview_status` control and inspect rendering. The timeline ruler shows chunk state and pressure. Preview rendering yields to playback; cache misses continue through normal evaluation.

Preview keys cover each frame, format, processing/source choice, and source dependencies. Unrelated edits preserve valid chunks; undo can reuse earlier content without encoding it again. The default profile is Full / intra H.264 at CRF 18. An explicit `IntraProResLike` or `Lossless` profile supports alpha; `Half` is an explicit playback scale. H.264 refuses transparent frames. The Lossless codec mode still uses the engine's 8-bit YUV conversion, so it is not a lossless working-linear master format.

Exact frame inspection and exports bypass playback chunks, and the export producer rejects a frame marked as cached. Cached playback keeps audio on the live mixer. Cache status includes pressure and failures rather than treating an accepted request as a completed render.

## Verification

The scripted agent workflows exercise real dispatch, revisions, atomic plans, retry receipts, undo, transcript/video alignment, contact-sheet pixels, and frozen batch exports. They validate API outcomes; they do not measure an LLM's reasoning or tool-selection success rate.

The CI video-outcome lane installs Mesa software Vulkan, requires GPU-backed assertions to execute, and runs acceptance stories with `--strict`. Missing adapters/codecs and skipped required story steps fail that lane. Software rendering verifies correctness, not realtime performance on a user's GPU.

Run the targeted workflows locally:

```sh
PHOTONIC_REQUIRE_GPU=1 cargo test -p photonic-mcp --locked \
  --test ai_contracts --test video_agent_workflows -- --test-threads=1
PHOTONIC_REQUIRE_GPU=1 cargo test -p photonic-video --locked --lib \
  production_session_serves_cache_with_codec_tolerance_and_undo_reuse
scripts/run-acceptance-stories.sh --strict
```

Use the [playback benchmark](playback-benchmark.md) to collect actual observed-frame cadence, stalls, seek latency, memory, and adapter metadata. Hardware timing gates require an explicit workload and measured budgets for a named machine. No portable realtime speedup is inferred from unit-test timing.
